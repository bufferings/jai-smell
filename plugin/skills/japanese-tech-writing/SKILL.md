# 日本語の技術文書の規範

日本語の技術文書（README、ドキュメント、記事、解説文）を作成・推敲するときは、以下の規範に従う。

## 段落と論証の構成

パラグラフライティングを基本とする。段落は論証の一段階であり、読者が段落単位で論理を追跡できるようにする。

- 一つの段落では一つのトピックのみを扱う。複数の話題（手順、結果、評価など）が混在する長い段落は、段落に分割する。
- 段落の最初の文で、その段落の内容が分かるようにする。
- 段落の先頭では、前の段落との論理関係を接続表現で明示する（「そのため」「実際に」「しかし」）。
- 論証は一方向に進める。結論を述べた後に反論を処理し、結論を再度述べる構成にしない。反論と疑問を処理した後に、結論を一度だけ述べる。
- 読者が抱きやすい誤った解釈は、明示的に否定したうえで本当の理由を述べる（「その理由は『〜だから』ではない。〜だからである」）。
- 「A ではなく B」と否定するときは、否定の根拠を一文添える。
- 二つの対象を対比して定義するときは、両方の文の述部を同じ形にする。
- 否定や限定をするときは、否定する命題そのものを「」で正確に示す（「設定を記述すればすべてを自動化できる」を意味しない、など）。「すべてが解決するわけではない」のような漠然とした否定にとどめない。
- 「後の節で説明する」のような前方参照は、論証が一段落した位置（段落や節の末尾）に記述する。論証の途中に挟まない。

## 論証の正確さ

記述を終えたら、読み手の反論を想定して次の点を点検する。

- 推量、可能性、仮定を表す文を、機械的に確定的な表現に変更しない。「かもしれない」「だろう」は、根拠なく主張を弱めている場合のみ削除する。未確認の可能性、ログからの推定、読者が抱きそうな疑問を表す場合は、不確実性を保持する。確定的な表現に修正できるのは、本文中の根拠によって命題が確定している場合に限る。
- 異なるものを「同じ」とまとめない。区別すべき対象（別々の決定、別々の原因、種類の異なる問題）を一つの言葉でくくらない。
- 複数の要因がある事象を、単一の原因に帰着させない。それぞれを分離し、どの説明がどの要因に対応するかを示す。
- 文書全体で、同じ概念の扱いを一致させる。分類、定義、用語の位置付けを節ごとに変更しない。
- 因果関係を主張するときは、その仕組みを一文で示す。悪い例：「手順で分割すると変更が全体に波及する」。良い例：「各工程がデータの受け渡しに同じ表現を共有するため、その表現を変更すると全体に波及する」。
- 検出、保証、解決が「必ず」できるかのように記述しない。条件を付けて正確に述べる（「〜しやすい」「〜できる場合が多い」「〜が成り立つ場合に限り」）。
- 挙げた例が主張の全体を支えているかを確認する。例が主張の一部しか支えない場合は、主張の範囲を例に合わせて狭める。
- 「次の節で説明する」とした論点が、実際にその節で説明されていることを確認する。
- 譲歩や限定（「ただし」「とはいえ」）を記述したら、その後で論を進める。逆接で終えない。
- 節の中心となる用語は、その節より前で定義と対象範囲を示してから使用する。
- 複数の概念を一つの上位の用語にまとめるときは、それらが同じものに帰着することを、命名の直前に一文で述べる。
- 確認していないことを、確認したかのように記述しない。

## 読み手の負荷の管理

読者の記憶と注意は有限であることを前提とする。

- 読者が順に読みながら保持する情報は、一度に一段階ずつ増やす。記述を削除したら残った言及を確認し、文書のほかの箇所で使用しなくなった話題は削除する。
- 後で参照しない固有名（ファイル名、関数名、識別子）を記述しない。「仕様書」「金額計算のユーティリティ」のような一般的な名称で示す。
- 抽象的な表現が指す内容を文脈から一意に特定できない場合は、丸括弧で補足し、読者に前の記述を読み返させない。
- 概念を初めて示す文では、その概念の種類（データ構造、手順、制約など）を先に示す。その概念を知っている読者にだけ分かる性質や仕組みを、種類より前に記述しない。
- 新しい例を追加するときは、前の例との違いと、追加する理由を先に示す。
- 図、表、コードなど複数の形式で説明するときは、それぞれが担う説明を区別する。指示語（「この 2 つ」「上記の例」）が、どの形式のどの例を指すかを一意に特定できるようにする。
- 二つの方式を「A の代わりに B」と対比するときは、採用する方式が後に来ることを読み取れる語順にする。
- 導入部に、後の説明に関係しない詳細を含めない。例の中でも、その節の問いや結論に関係しない詳細（時刻、HTTP ステータス、カバレッジ率など）は省略し、議論に必要な具体的な情報は残す。

## 用語と表現

- 例示では、結果の羅列や受動態（「特定され、判明した」）ではなく、行為者を主語にした動作の連続（「ログを調査して原因を特定した」）で記述する。
- 論証の中で読者を「あなた」と呼ばず、役割名（「開発者」「利用者」）で記述する。
- 対象を指す言葉は具体的に選択する。「AI」「ツール」のような意味の広い言葉で対象を曖昧にしない。
- 用語を導入したら、以後はその用語で統一する。「文脈」「ツール」のような曖昧な言葉に置き換えない。
- 用語と訳語は、その分野やツールの日本語ドキュメントで用いられているものを選択する。意味の近い漢語を一般的な感覚で当てはめない。英語の用語を日本語の文に混ぜない。設定の値、フィールド名、コマンド名などの識別子は、英語のまま記述する。
- 開発者のあいだで定着したカタカナ語がある場合は、漢語に置き換えない（「デフォルト」を「既定」、「ルート」を「経路」としない）。
- 技術文書で一般的な表現を選択する。話し言葉（「見る」「使う」「書く」「作る」「直す」）ではなく、「確認する」「使用する」「記述する」「作成する」「修正する」のように、対象と操作が明確な表現を用いる。
- イ形容詞に「です」を続けた文（「難しいです」「多いです」）を記述しない。これは文の流れが途切れている兆候である。流れのある文章であれば、「〜は難しく、…」と後の文につながるか、「〜でしょう」「〜である」で受けられる。文末だけを修正せず、前後の文の構成を見直す。ナ形容詞の「〜です」（「重要です」）は対象外とする。

## 演出の抑制

- 溜め（「ここには〜が潜んでいる」）や修辞疑問で結論を演出しない。説明で足りる箇所では、そのまま述べる。
- 短い決め台詞を独立した段落にしない。
- 太字の強調を多用しない。誤読を防ぐための否定や節の結論など、論理上重要な箇所に限り、一つの節で一、二箇所までとする。
- 起こりうる結果を列挙して危険性を誇張しない。
- 「重要なのは〜である」のような前置きで主張を予告しない。主張をそのまま記述する。
- 「A ではなく B だった」という対句の決め台詞を多用しない。
- 慣用表現をひねった言い回し（「知識を体に入れる」など）や、指す内容を一意に特定できない比喩（「報告の外側に世界が広がっている」など）を用いない。

## LLM に特有の空虚な表現の禁止

次のような表現は、論点を増やさず、体裁だけを整える。記述を終えたら、この節の項目を点検する。

- 予告と総括：「重要なのは〜である」「本章では〜を扱う／探求する」「ここでは〜について見ていく」「まとめると」「要するに」（直前の内容の言い換えのみの場合）、「〜に他ならない」
- 姿勢の宣言：「正面から扱う」「正面から回収する」
- 強調のみの形容：「不可欠」「核心的」「鍵となる」「根本的な」（主張の内容を説明せず強調だけする場合）、「多角的」「包括的」「総合的」（何をどのように確認したかを示さない場合）
- 内容を示さない動詞：「掘り下げる」「深掘りする」「言語化する」（何をどのように記述したかを示さない場合）
- 新しい情報のない接続：「〜において」「〜という側面から」「〜の観点から」、「さらに」「また」「加えて」の連続
- 根拠のない緩和と強調：「〜と言えるだろう」「〜かもしれない」（根拠なく主張を弱める場合のみ。推量、仮定、読者の疑問を表す場合は保持する）、「非常に」「極めて」「大いに」

## 翻訳調の比喩と擬人化の禁止

LLM は、日本語として定着していない言い回しを次の三つの形で生成する。前節の表現と異なり、比喩を用いる意図がないまま混入するため、比喩を用いたつもりのない文も点検する。

- 英語の慣用句の直訳：英語の技術文では carry、open、expose、live、run などの比喩的な用法が慣用句として定着している。これを日本語に直訳すると、日本語では慣用化していないため、字義どおりに読める不自然な比喩になる。
  - 悪い例：「ベクトルが選好を運ぶ」（carry）。良い例：「選好がベクトルに反映される」。
  - 悪い例：「この問いは開かれている」（open question）。良い例：「この問いは未解決である」。
  - 悪い例：「この情報は残差ストリームに住んでいる」（live in）。良い例：「この情報は残差ストリームに含まれる」。
  - 悪い例：「CI が走る」（run）。良い例：「CI が実行される」。
- 無生物主語の構文の直訳：英語では無生物主語の他動詞文が一般的だが、そのまま日本語にすると、モデル、データ、設定などの抽象物が意思を持つかのような擬人化になる。人や処理を主語に戻すか、「〜から分かる」「〜に含まれる」の形に修正する。
  - 悪い例：「モデルは文体を知っている」。良い例：「モデルの出力には文体の一貫性がある」。
  - 悪い例：「データが語るのは〜である」。良い例：「データから分かるのは〜である」。
- 口頭の議論で用いる俗語の混入：「効く」「刺さる」「筋がいい」などは、口頭では通じるが、技術文書では俗語である。効果や見込みの内容を具体的に記述する。
  - 悪い例：「このオプションが効く」。良い例：「このオプションを指定すると、ビルド時間が短縮される」。
  - 悪い例：「この手法は筋がいい」。良い例：「この手法は〜という理由で有望である」。

判定の目安は二段階である。まず、その述語に初めて接する読者が字義どおりの動作（運ぶ、開く、住む）を想像する可能性があれば、翻訳調の比喩である可能性を検討する。次に、動作の主体と対象を具体的な言葉で言い換えられるかを確認する。言い換えられる場合は、その言い換えを記述する。言い換えられない場合は、その文が指す内容を特定できておらず、主張として成立していない。削除するか、内容を確定させてから修正する。

## 冗長さの排除

- 同じ主張を言い換えて繰り返さない。一つの主張は一度だけ記述する。題材が直前と同じでも、新しい命題を加えている文は繰り返しではない。
- 隣接する節が同じ内容を別の角度から述べている場合は、一つの節にまとめる。
- 具体例を示した直後に、その内容を再度要約しない。
- 同じ論理的役割を持つ並列の事実は、文を分割せずに一文にまとめる。
- 冗長さを文字数や文の数で判定しない。短くするのは、動機、対象、操作、因果、条件を読み取れる状態を保てる場合に限る。これらを読者の推論に委ねる圧縮はしない。
- 接続や評価のためだけの文（「それ自体はよいことである」など）を記述しない。
- 想像上の読者との問答（問いを立てて一つの単語で回答する形式など）を修辞として用いない。読者の反応を想定して応答する形式（「〜と感じたかもしれない。そのとおりである」）も避ける。
- 読者が抱きそうな発想を、メタな前置き（「ここまでの話には自然な続きがある」）で紹介しない。その発想を直接記述する。
- 著者の立場の弁明や断りを記述しない。
- 本文でまだ導入していない概念や文書名を、先に示さない。
- 根拠によって確定していることを、ためらいのある弱い述語（「有効な対策であり」など）で表現しない。強く具体的に述べる（「必須であり」など）。ただし、不確実性、可能性、仮定を表す弱い述語は保持する。

## 見出しの付け方

- 見出しは、その節が答える問い、または扱う対象を示す具体的な句にする。
- 作業の手順のみを述べる見出し（「例に戻る」「〜を読み直す」など）や、情報量のない見出しにしない。
- 見出しを、節の結論を言い切る文にしない。
- 疑問形と名詞句のどちらを用いるかは、本文の文体に合わせて選択する。
